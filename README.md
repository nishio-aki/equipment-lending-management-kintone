
# 社内機材・備品 統合貸出管理システム

 **kintoneをベースにした社内機材・備品の貸出・返却管理システム**

 単純な備品台帳ではなく、**利用者の申請負担と管理担当者の検索・照合作業を削減すること**を目的とした業務改善システム。

---

 ## Overview

 ### 解決したい課題

 - Excel・スプレッドシート・チャット等に分散した貸出管理
- 管理担当者が毎回「空いている個体」を探す作業
- 同一型番の機材を複数台貸し出す際の照合作業
- 返却忘れ・貸出履歴の管理漏れ
- 「必要だったが貸し出せなかった」という需要が記録されない問題

 ### 基本方針

 > **利用者には「何を・何台・いつまで使いたいか」だけ入力してもらい、個体の検索・候補選出はシステムに任せる。最終的な貸出許可は人間が行う。**

 「すべてを自動化する」のではなく、**システムが検索・照合を担い、人間は最終判断に集中する**設計とする。

## 従来の貸出管理システムとの違い

多くの現場で使われている従来の貸出管理ツールと、本システム（設計思想）の比較は以下の通りです。単なる機能の有無ではなく、「利用者・管理者の認知負荷の削減」と「データの資産化」を軸に設計しています。

| 観点 | 一般的な貸出管理（従来） | 本システム（設計思想） |
| :--- | :--- | :--- |
| **貸出対象の指定** | 利用者が個体を目視で選択する | 利用者は品目・数量・期間を指定し、個体はシステムが自動選定 |
| **複数台の貸出** | 1台ずつバラバラに申請するケースが多い | 複数台をまとめて一括申請できる |
| **候補選定** | 管理者が一覧を目視で探して突合する | システムが利用可能期間から候補を自動抽出・提示 |
| **最終判断** | 自動処理または属人的な単純承認 | 候補選定はシステム、最終的な割当判断は人間（管理者） |
| **貸出不可時の挙動** | 在庫なしとしてそのまま申請終了（却下） | 申請内容を保持したまま、貸出不可として理由を通知 |
| **貸出不可の扱い** | 単なる「失敗・エラー」として消える | 「実際に発生した需要・供給不足のデータ」として履歴を保持 |
| **キャンセル対応** | 管理者へ個別連絡・手動消去が必要 | 申請者本人がステータス制御に基づき自力でキャンセル可能 |
| **利用者UX** | 空いているものを自力で探す負担がある | 探す手間がゼロに。承認されなくても通知から代替案をワンクリックするだけ |
| **管理者の作業** | 個体確認・候補探索・判断を手作業でする | 探索や照合はシステム化し、人間は確認・例外判断に集中する |
| **自動化の方針** | 何でもかんでも「可能な限り自動化」する | 「人間が担うべき判断とシステム処理の境界」を明確に設計 |
| **データの活用** | 現在の貸出状況を管理するだけで終わる | 貸出履歴や不足データから、将来的な需要把握・投資に活かす |

 # Data Structure

 ## 1\. 品目マスタ（利用者が参照）

 「何の機材か」を管理するマスター。

 - 品目ID(システムで自動付与･･･6桁で意味を持たない一意の数字でゼロ埋め。)
- 大 / 中 カテゴリ（kintoneの標準機能では大カテゴリを中カテゴリに波及させることが困難なのでJSで制約を設け登録ミスを防ぐ設計）
- 品目名
- メーカー
- 型番
- 対応業者

 ## 2\. 個体マスタ（管理者専用）

 同一品目に存在する実物を個体単位で管理する。（裏でGASや管理者が突合する用）

 - 機材ID
- 品目
- 資産番号
- シリアル番号
- 状態
- 保管場所
- 購入日
- 備考

 例えば、

```
ThinkPad X1 Carbon
├─ PC-001
├─ PC-002
├─ PC-003
├─ ...
└─ PC-030
```

 のように、**品目と個体を分離**する。

 個体管理は利用者に行わせるためではなく、管理側で利用履歴・状態・所在を追跡するために行う。

 ## 3. 貸出・返却申請（ユーザー・管理者共有）

実際の貸出業務を管理するトランザクション。利用者の申請フォームおよび管理者の処理画面として共通利用する。

| 項目名 | 入力・制御元 | 閲覧・操作権限 | 備考・バリデーション |
| :--- | :--- | :--- | :--- |
| **申請ID / リクエストID** | 自動生成 | 全体閲覧 (編集不可) | 重複不可の一意キー（二重実行防止用） |
| **申請者 / 所属部署** | 自動取得 | 全体閲覧 (編集不可) | ログインユーザー情報から自動補完 |
| **大・中カテゴリ** | ユーザー入力 | **ユーザー入力可** | 品目選択時のフィルター（絞り込み）として機能 |
| **対象品目** | ユーザー入力 | **ユーザー入力可** | カテゴリ連動のルックアップ（またはドロップダウン） |
| **必要台数** | ユーザー入力 | **ユーザー入力可** | 数値入力 |
| **貸出開始日** | ユーザー入力 | **ユーザー入力可** | 2週間以内 ＆ 営業日カレンダー検証（休日指定不可） |
| **返却予定日** | ユーザー入力 | **ユーザー入力可** | 営業日カレンダー検証（休日指定不可） |
| **利用目的 / 詳細** | ユーザー入力 | **ユーザー入力可** | テキスト入力 |
| **割当個体** | システム/管理者 | **管理者のみ** | 候補選定後に管理者が確定・割当 |
| **実返却日** | 管理者入力 | **管理者のみ** | 返却受領時にJSで自動書き込み |
| **ステータス** | プロセス管理 | *権限分離あり*（※下記参照） | 申請の現在地をリアルタイム表示 |

### ステータスのライフサイクルと権限
ユーザー画面および管理者のプロセス管理では、以下のステータスを遷移・表示します。

* **`未承認`**：申請直後、管理者の確認待ち（※ユーザーはここから自力で「キャンセル」へ移行可能）
* **`代替案提示中`**：在庫不足に伴い、ユーザーの二択選択（一部予約 or 最短日）待ち
* **`承認済み（確定）`**：機材確保・承認完了（※貸出前であればユーザーが自力で「キャンセル」可能）
* **`貸出中`**：管理者が機材を手渡し、利用中の状態
* **`返却完了`**：無事に返却され、一連のフローが完了した状態
* **`キャンセル`**：ユーザーまたは管理者によって取り消された状態（権限：申請者本人・管理者）
* **`貸出不可`**：代替案が選択・確定されず、供給不足として不成立でクローズした状態

 # Core Logic & Workflow

## 1. リードタイム・期間制限と営業日カレンダー制御
- **最大2週間（14日）のリードタイム制限**：起算日（`today()`）から最大2週間先までの貸出開始日に限定。「念のための長期キープ（幽霊予約）」によるリソース枯渇を選考段階で防ぐ。（大きなイベントなど特別な事情がある場合は上長の承認を受け、特別申請とする。）
- **営業日カレンダーマスタによる日付制御**：土日祝を起算日や返却日に指定できないようバリデーションをかけ、休日をまたぐ計算の正確性を担保する。

## 2. 複数台一括申請と自動候補選出
利用者は個体を選択せず、`品目・台数・期間`の単位で申請する。

例
```
品目：ThinkPad X1 Carbon
台数：5台
期間：10/1 ～ 10/5
```

 ### 候補選出

 申請内容をもとにシステムが個体を検索する。

```
① 対象品目が一致する個体を抽出
② 使用不可個体を除外（修理中・メンテナンス中・特別申請）
③ 既存貸出期間との重複を判定
④ 利用可能な個体を抽出
⑤ 返却予定日の近い順で候補を提示
⑥ 必要台数を確保できるか判定
```

 例：

```
必要：5台

PC-003  利用可能
PC-005  利用可能
PC-008  利用可能
PC-007  10/01返却予定
PC-012  10/02返却予定
```

 候補選出までは自動化するが、**最終的な個体割当・貸出許可は管理者が行う。**
 
 ## Design Philosophy: 「完全自動化」にしない理由（設計意図）

本システムでは、検索や候補選出ロジックを自動化する一方で、最終的な個体割当や貸出許可には**必ず「人間の管理者」を介在させる設計**としている。これには以下の合理的な理由がある。

1. **物理的・現実的な制約（実態の担保）**
   - 実際に備品を手渡し、回収し、メンテナンスするのは人間である。直前の破損や隠れた不具合など、システムが完全には捉えきれない「現実の物理的制約」を吸収するフィルターとして機能させる。
2. **例外処理・クレンジングの安全弁**
   - 突発的なイレギュラーやルールの隙間に入る例外処理に対し、柔軟に対応できる人間を挟むことで、システム全体が破綻（例外エラーで停止）するのを防ぐ。
3. **心理的クッションと組織的寛容さ**
   - 完全無人・機械的なシステム相手には、人間は冷たくなり不満を抱きやすい（場合によっては裏で隠れて貸出を行い始める可能性がある）。プロセスの中に「一瞬でも人間（管理者）」を挟むことで、システムに対する心理的な納得感や、組織としての寛容なコミュニケーションを生み、現場に定着する健全な運用を目指す。
4. **人間を介した改善点の回収**
   - 管理者が申請を処理する過程で、「ユーザーがどこで迷っているか（UIの違和感）」や「ログの数字には表れない定性的なボトルネック」をキャッチできる。このフィードバックを次期のシステム改善や調達計画のインプットとして循環させる。

 # 貸出不可の扱い

 必要台数を確保できない場合は「貸出待ち」を設けず、申請を貸出不可として完結させる。

 ただし、申請データは破棄しない。

 ここで重要なのは、**貸出不可通知を新たな要望入力に置き換えないこと**。

 申請時に入力された情報をそのまま利用し、

 - 対象機材
- 必要台数
- 貸出予定期間
- 利用目的
- 詳細

 を通知に反映する。

 ### 例

 申請：

```
対象機材：
ThinkPad X1 Carbon

必要台数：
5台

貸出予定期間：
2026/10/01 ～ 2026/10/05

利用目的：
新入社員研修

詳細：
新入社員5名が研修期間中に使用するため。
```

 貸出不可時：

```
申請された条件を満たす機材を
確保できませんでした。

対象機材：
ThinkPad X1 Carbon

必要台数：
5台

貸出予定期間：
2026/10/01 ～ 2026/10/05

利用目的：
新入社員研修

詳細：
新入社員5名が研修期間中に使用するため。
```

 **申請者が「要望」を改めて入力する必要がなく、もともとの申請内容がそのまま記録として残る。**

 これにより、

 > 「申請したが貸出できなかっただけ」

 で終わらせず、**実際に発生した需要と供給不足をデータとして残す**。

 # DX / Design Points

 ### 1\. 個体管理を利用者に押し付けない

 利用者は「PC-001を借りたい」と考える必要がない。

 **品目・数量・期間を入力するだけ**で申請できる。

 ### 2\. 管理担当者の検索・照合作業を削減する

 従来担当者が行っていた、

 > 「この型番で、申請期間中に使える個体はどれか？」

 という検索をシステム側で処理する。

 ### 3\. 自動化と人間の判断を分離する

 **システム**

 - 個体検索
- 利用可能判定
- 期間重複判定
- 候補抽出
- 候補の並び替え
- 必要台数の確保可能判定

 **人間**

 - 候補個体の最終確認
- 個体割当
- 貸出許可
- 例外的な事情への判断

 ### 4\. 貸出不可もデータとして残す

 「貸出不可」を単なる却下で終わらせず、申請内容を保持する。

 これにより将来的に、

 - 品目別の利用件数
- 貸出不可件数
- 平均貸出期間
- 需要の集中時期
- 供給不足が発生している機材

 などを分析できる。

 ### 5\. 資産の透明化と棚卸負担の軽減

 すべての申請履歴が個体マスターと完全に紐づくことで、

 - 「今、どの機材が誰の手にあるか」の所在を常にクリアにする
- 定期的な棚卸や行方不明機材の探索にかかる管理調整コストを劇的に削減する

 
 

 ## 6. 期待される効果とインパクト 

本システムの導入により、50人規模の組織において**年間約300時間の労働時間削減**および、属人的だった備品管理の「データ資産化」を実現します。

### ① 労働時間削減の試算根拠（年間 約300時間）
「探す・確認する・突合する」という、人間の脳のメモリを食う非生産的な作業をシステムが代替します。

* **利用者側：年間 約150時間の削減**
  * **想定前提：** 50人の組織で、1人あたり月1回（年間12回）の機材申請・空き確認を行う。
  * **工数削減：** 従来、チャットや口頭での確認・調整に往復で約15分かかっていたところを、申請フォームからの即時自動判定に置き換えることで、**1回あたり15分を削減**。
  * **計算式：** \(毎月50件 × 12ヶ月 × 0.25時間（15分短縮） = 年間150時間\)
* **管理者側：年間 約150時間の削減**
  * **想定前提：** 全社で月50件の貸出・申請処理が発生する。
  * **工数削減：** 従来、カレンダーや台帳を目視で突合し、空き個体をパズルのように探して調整する作業に1件あたり約20分かかっていたところを、システムによる候補選出・ステータス管理の導入により**1件あたり5分に短縮**（確認・承認作業のみへ移行。1件あたり15分の削減）。
  * **計算式：** \(毎月50件 × 12ヶ月 × 0.25時間（15分短縮） = 年間150時間)

 # Future Extension

 現時点ではデータ分析基盤の構築を目的としない。

 まずは、

 > **貸出業務を正しくデータ化し、担当者の検索・照合作業を削減する**

 ことを優先する。

 その上で、蓄積されたデータを将来的な、

 - 貸出需要の可視化
- 備品の更新判断
- 供給不足の把握
- 利用実態分析
- 業務改善

 へ繋げられる構造としておく。

 # Portfolio Goal

 単にkintoneで貸出管理アプリを作るのではなく、

 > **既存業務を分解し、どこを標準機能で処理し、どこを自動化し、どこに人間の判断を残すかを設計する**

 ことを目的とする。

 \*\*「備品を管理するシステム」ではなく、「備品貸出業務そのものを改善するシステム」\*\*を目指す。
