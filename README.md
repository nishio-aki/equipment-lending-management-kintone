## 制作について

 おつかれさまです。

 kintoneのポートフォリオですが、志望企業の深掘りが不可能（そもそも業務の裏側は外部からは見えない）であったため、まずは汎用性の高い貸出管理システムを作ろうと考えました。

 しかし、設計を進めるうちにやりたいことが膨れ上がってしまったため、データ分析については将来の拡張として、今回は業務システムとしての設計・実装に絞っています。

 主な設計ポイントは以下の通りです。


 💡 一般的な貸出管理との設計方針の違い

本システムでは、単純に「貸出・返却を記録する」だけではなく、利用者・管理者双方の運用負担を減らしながら、継続的に使われることを意識して設計しています。

観点	一般的な貸出管理	本システム
貸出対象の指定	利用者が個体を選択	利用者は品目・数量・期間を指定し、個体はシステム側で候補選出
複数台の貸出	1台ずつ申請するケースがある	複数台をまとめて申請
候補選定	管理者が一覧から探す	システムが貸出条件から候補を選定
最終判断	自動処理または単純承認	候補選定はシステム、最終判断は管理者
貸出不可	在庫なしとして申請終了	現在貸出中の申請内容を利用して、理由を含めて通知
貸出不可の申請	失敗として終了	実際に発生した需要として履歴を保持
利用者UX	利用可能なものだけを申請	貸出不可でも申請自体は受け付け、徒労感を抑える
管理者の作業	個体確認・候補探索・判断を手作業	候補探索や照合をシステム化し、人間は確認・判断に集中
自動化の方針	可能な限り自動化	人間が担うべき判断とシステム処理の境界を設計
データの活用	現在の貸出状況を管理	貸出履歴・貸出不可申請を含め、将来的な需要把握にも利用可能

設計思想

本システムでは、**「すべてを自動化すること」ではなく、「人間が行う必要のない処理をシステムへ移し、人間には判断や現物確認などの役割を残すこと」**を重視しています。

また、貸出できなかった申請も単なるエラーとして破棄せず、実際に発生した需要として記録します。

これにより、日々の貸出業務を効率化するだけでなく、利用状況や不足している備品を後から把握できる状態を作ることを目指しています。

 - **利用者に個体を選ばせるのはおかしい（手間）**
  - 品目だけを選択してもらい、具体的な個体はシステム側で選定する。
- **管理者が毎回、貸し出せる個体を探すのは手間**
  - 属人的かつ工数の無駄になるため、候補の選定まではシステムで行い、最終判断を人間に委ねる。
- **毎回1台ずつ申請して借りるのは面倒**
  - 複数台をまとめて申請できるようにし、必要台数を満たす個体候補をシステム側で選出する。
- **貸出不可の場合、そもそも申請できない設計もできるが、申請自体に徒労感が生まれ、使われないシステムになる恐れがある**
  - 貸出不可の場合でも、申請時に入力された貸出期間・利用目的・詳細などを通知内容に反映することで、「何のために申請したのか」がそのまま残る設計にする。
  - 会社側にとっても、貸出不可となった申請を「実際に発生した需要」として蓄積でき、将来的な備品購入・更新時の客観的な判断材料として活用できる。
  - 利用者にとっても「申請したこと自体が無駄にならない」状態を作ることで、継続的に利用されるシステムを目指す。
  - そのため、貸出中であっても申請自体は受け付ける設計とする。
- **基本はkintoneの標準機能を利用する**
  - 過度に属人的なコードへ依存することは避け、kintoneの標準機能を最大限利用する。
  - JavaScript等は標準機能では実現しにくい候補選出などの業務ロジックを補完するために使用する。
  - 実装を通してkintoneそのものの理解を深めることも目的とする。

 以上を踏まえ、まずは**kintone 1作目として、ある程度の実装難度を確保しつつ、業務オペレーション（Ops）の設計思想も含めたポートフォリオ**としてまとめています。

 ここから先は、実装しながら設計上の問題点や改善点を洗い出していく予定です。

 **設計・実装について、FBいただけると幸いです。**



# 社内機材・備品 統合貸出管理システム

 **kintoneをベースにした社内機材・備品の貸出・返却管理システム**

 単純な備品台帳ではなく、**利用者の申請負担と管理担当者の検索・照合作業を削減すること**を目的とした業務改善システム。

---

 ## Overview

 ### 解決したい課題

 - Excel・スプレッドシート・チャット等に分散した貸出管理
- 管理担当者が毎回「空いている個体」を探す作業
- 同一型番の機材を複数台貸し出す際の照合作業
- 返却忘れ・貸出履歴の管理漏れ
- 「必要だったが貸し出せなかった」という需要が記録されない問題

 ### 基本方針

 > **利用者には「何を・何台・いつまで使いたいか」だけ入力してもらい、個体の検索・候補選出はシステムに任せる。最終的な貸出許可は人間が行う。**

 「すべてを自動化する」のではなく、**システムが検索・照合を担い、人間は最終判断に集中する**設計とする。

## 従来の貸出管理システムとの違い

多くの現場で使われている従来の貸出管理ツールと、本システム（設計思想）の比較は以下の通りです。単なる機能の有無ではなく、「利用者・管理者の認知負荷の削減」と「データの資産化」を軸に設計しています。

| 観点 | 一般的な貸出管理（従来） | 本システム（設計思想） |
| :--- | :--- | :--- |
| **貸出対象の指定** | 利用者が個体を目視で選択する | 利用者は品目・数量・期間を指定し、個体はシステムが自動選定 |
| **複数台の貸出** | 1台ずつバラバラに申請するケースが多い | 複数台をまとめて一括申請できる |
| **候補選定** | 管理者が一覧を目視で探して突合する | システムが利用可能期間から候補を自動抽出・提示 |
| **最終判断** | 自動処理または属人的な単純承認 | 候補選定はシステム、最終的な割当判断は人間（管理者） |
| **貸出不可時の挙動** | 在庫なしとしてそのまま申請終了（却下） | 申請内容を保持したまま、貸出不可として丁寧に通知 |
| **貸出不可の扱い** | 単なる「失敗・エラー」として消える | 「実際に発生した需要・供給不足のデータ」として履歴を保持 |
| **利用者UX** | 空いているものを自力で探す負担がある | 探す手間をゼロにし、徒労感やストレスを抑える |
| **管理者の作業** | 個体確認・候補探索・判断を手作業でする | 探索や照合はシステム化し、人間は確認・判断に集中する |
| **自動化の方針** | 何でもかんでも「可能な限り自動化」する | 「人間が担うべき判断とシステム処理の境界」を明確に設計 |
| **データの活用** | 現在の貸出状況を管理するだけで終わる | 貸出履歴や不足データから、将来的な需要把握・投資に活かす |
---

 # Data Structure

 ## 1\. 品目マスター

 「何の機材か」を管理するマスター。

 - 品目ID
- 大 / 中 / 小カテゴリ
- 品目名
- メーカー
- 型番
- 対応業者
- その他属性

 ## 2\. 個体マスター

 同一品目に存在する実物を個体単位で管理する。

 - 機材ID
- 品目
- 資産番号
- シリアル番号
- 状態
- 保管場所
- 購入日
- 備考

 例えば、

```
ThinkPad X1 Carbon
├─ PC-001
├─ PC-002
├─ PC-003
├─ ...
└─ PC-030
```

 のように、**品目と個体を分離**する。

 個体管理は利用者に行わせるためではなく、管理側で利用履歴・状態・所在を追跡するために行う。

 ## 3\. 貸出・返却申請

 実際の貸出業務を管理するトランザクション。

 - 申請者
- 部署
- 対象品目
- 必要台数
- 貸出開始日
- 返却予定日
- 利用目的
- 詳細
- 貸出結果
- 割当個体
- 実返却日
- ステータス

 # Core Logic

 ## 複数台申請

 利用者は個体を選択しない。

```
対象：ThinkPad X1 Carbon
台数：5台
期間：10/1 ～ 10/5
```

 という単位で申請する。

 ### 候補選出

 申請内容をもとにシステムが個体を検索する。

```
① 対象品目が一致
② 使用不可個体を除外
③ 既存貸出期間との重複を判定
④ 利用可能な個体を抽出
⑤ 返却予定日の近い順等で候補を提示
⑥ 必要台数を確保できるか判定
```

 例：

```
必要：5台

PC-003  利用可能
PC-005  利用可能
PC-008  利用可能
PC-007  10/01返却予定
PC-012  10/02返却予定
```

 候補選出までは自動化するが、**最終的な個体割当・貸出許可は管理者が行う。**
 
 ## Design Philosophy: 「完全自動化」にしない理由（設計意図）

本システムでは、検索や候補選出ロジックを自動化する一方で、最終的な個体割当や貸出許可には**必ず「人間の管理者」を介在させる設計**としている。これには以下の合理的な理由がある。

1. **物理的・現実的な制約（実態の担保）**
   - 実際に備品を手渡し、回収し、メンテナンスするのは人間である。直前の破損や隠れた不具合など、システムが完全には捉えきれない「現実の物理的制約」を吸収するフィルターとして機能させる。
2. **例外処理・クレンジングの安全弁**
   - 突発的なイレギュラーやルールの隙間に入る例外処理に対し、柔軟に対応できる人間を挟むことで、システム全体が破綻（例外エラーで停止）するのを防ぐ。
3. **心理的クッションと組織的寛容さ**
   - 完全無人・機械的なシステム相手には、人間は冷たくなり不満を抱きやすい。プロセスの中に「一瞬でも人間（管理者）」を挟むことで、システムに対する心理的な納得感や、組織としての寛容なコミュニケーションを生む。
4. **人間を介した「改善センサー」の回収**
   - 管理者が申請を処理する過程で、「ユーザーがどこで迷っているか（UIの違和感）」や「ログの数字には表れない定性的なボトルネック」をキャッチできる。このフィードバックを次期のシステム改善や調達計画のインプットとして循環させる。
---


 # 貸出不可の扱い

 必要台数を確保できない場合は「貸出待ち」を設けず、申請を貸出不可として完結させる。

 ただし、申請データは破棄しない。

 ここで重要なのは、**貸出不可通知を新たな要望入力に置き換えないこと**。

 申請時に入力された情報をそのまま利用し、

 - 対象機材
- 必要台数
- 貸出予定期間
- 利用目的
- 詳細

 を通知に反映する。

 ### 例

 申請：

```
対象機材：
ThinkPad X1 Carbon

必要台数：
5台

貸出予定期間：
2026/10/01 ～ 2026/10/05

利用目的：
新入社員研修

詳細：
新入社員5名が研修期間中に使用するため。
```

 貸出不可時：

```
申請された条件を満たす機材を
確保できませんでした。

対象機材：
ThinkPad X1 Carbon

必要台数：
5台

貸出予定期間：
2026/10/01 ～ 2026/10/05

利用目的：
新入社員研修

詳細：
新入社員5名が研修期間中に使用するため。
```

 **申請者が「要望」を改めて入力する必要がなく、もともとの申請内容がそのまま記録として残る。**

 これにより、

 > 「申請したが貸出できなかっただけ」

 で終わらせず、**実際に発生した需要と供給不足をデータとして残す**。

---

 # DX / Design Points

 ### 1\. 個体管理を利用者に押し付けない

 利用者は「PC-001を借りたい」と考える必要がない。

 **品目・数量・期間を入力するだけ**で申請できる。

 ### 2\. 管理担当者の検索・照合作業を削減する

 従来担当者が行っていた、

 > 「この型番で、申請期間中に使える個体はどれか？」

 という検索をシステム側で処理する。

 ### 3\. 自動化と人間の判断を分離する

 **システム**

 - 個体検索
- 利用可能判定
- 期間重複判定
- 候補抽出
- 候補の並び替え
- 必要台数の確保可能判定

 **人間**

 - 候補個体の最終確認
- 個体割当
- 貸出許可
- 例外的な事情への判断

 ### 4\. 貸出不可もデータとして残す

 「貸出不可」を単なる却下で終わらせず、申請内容を保持する。

 これにより将来的に、

 - 品目別の利用件数
- 貸出不可件数
- 平均貸出期間
- 需要の集中時期
- 供給不足が発生している機材

 などを分析できる。

 # Future Extension

 現時点ではデータ分析基盤の構築を目的としない。

 まずは、

 > **貸出業務を正しくデータ化し、担当者の検索・照合作業を削減する**

 ことを優先する。

 その上で、蓄積されたデータを将来的な、

 - 貸出需要の可視化
- 備品の更新判断
- 供給不足の把握
- 利用実態分析
- 業務改善

 へ繋げられる構造としておく。

---

 # Portfolio Goal

 単にkintoneで貸出管理アプリを作るのではなく、

 > **既存業務を分解し、どこを標準機能で処理し、どこを自動化し、どこに人間の判断を残すかを設計する**

 ことを目的とする。

 \*\*「備品を管理するシステム」ではなく、「備品貸出業務そのものを改善するシステム」\*\*を目指す。
